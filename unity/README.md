# SoccerMaster native (Unity 6) — side-by-side project

The web app in the repository root stays the behavioral oracle and keeps shipping through Cloudflare
Pages. This folder is the native iPhone implementation (v1.2 package, tickets N00–N08). Nothing here
replaces or alters the web build; native delivery goes Unity Build Automation → App Store Connect →
TestFlight, and every step of it runs in a cloud service (no local Mac, Xcode or Unity Editor).

Boundary rule (architecture/INTEGRATION.md): `SoccerMaster.Core` owns state, RNG, rules, tactical
recognition, ranking and outcomes. `TacticalMomentController` only feeds wall-clock frames into
`MatchRuntime`, forwards a tap as an option id, and saves/restores the runtime. `TacticalMomentRig`
builds camera/field/players/ball/HUD at runtime and mirrors `MatchRuntime.View()` — it never reads a
score, feasibility or ranking to decide anything. No soccer reasoning lives in a MonoBehaviour.

## The native game loop (TacticalMoment scene)

```
Routine (skip clock ×180, veil, wide field)  →  LeadIn (camera eases to the selected player, speed ramps down)
  →  Question (frozen picture, 700 ms settle, answers visible but not armed)
  →  Timer (answers armed, timer bar; a tap → MatchRuntime.Answer(optionId))
  →  Resolving (canonical engine executes the committed intent at the frozen tick, 1× speed)
  →  Feedback (Decision / Execution / Outcome bands from the MomentRecord, NEXT)  →  Routine …
HalfTime / Finished are runtime phases too; Finished offers NEW MATCH.
```

* Exactly four answers per moment (`PacingConfig.NativeFour`): recognizer options plus same-role
  catalog entries instantiated against the same live state, unique commands, re-scored at commit
  time; the UI shows only the player-facing label — never the score or rank.
* Timeout: the engine acts (`Decision.Band == "timeout"`, actor `engine`) and the record is still
  settled and shown; nothing is skipped or invented.
* Save/reload: `MatchSave` v1 (`soccermaster-native-match`) serialises the whole runtime (canonical
  state, RNG word, session/recognizer counters, open and completed records, phase clocks). Written
  atomically (`.tmp` → replace) on `OnApplicationPause(true)`, focus loss and quit; a valid unfinished
  save resumes on launch; a save taken during `Timer` resumes as a frozen `Question` (the player
  re-reads before the clock restarts); format/version/catalog mismatches are rejected and the running
  match is kept. Backgrounding also sets `MatchRuntime.Paused` so the canonical clock does not run.
* Build identity overlay (bottom-left): `v<version> (<build>) · <sha7> · Unity <version>` from
  `Resources/build_info.json` written by `IosBuild`/`CloudBuild`; `(dev) · unknown` in the Editor.
* Safe area: all HUD lives under a `SafeArea` RectTransform driven by `Screen.safeArea` on a
  390×844 reference canvas.

## First ported interaction: first-touch training

`src/training/firstTouch.ts` → `Assets/SoccerMaster/Runtime/Core/Training/FirstTouchDrill.cs`
(plus `Rng`, `Vec2D`, `JsMath`, `GestureReader`). Preserved contract: 24×18 area, receive (10,9),
server (3,9), three gates, 50 ms tick, 2.5 s real-time decision window (×1.5 accessible), 0.12×
simulated time during the window, seeded RNG, anticipatory defender, decision / execution /
outcome kept separate, timeout still commits a loose touch.

Parity is checked against fixtures the **web implementation generates**, never hand-written values:

```
npm run native:fixtures   # tools/native*Fixtures.ts → Tests/Fixtures/{first_touch,tactics,math}_parity.json
npm run native:parity     # .NET harness: math, first touch, tactical moments, runtime save/reload parity
```

Tolerances: discrete state, phases, bands, gates, RNG words — exact. Kinematic doubles — 1e-9
(last-ULP differences between V8 and .NET transcendental functions).

## Signing — App Store distribution, prepared entirely in the cloud

TestFlight requires an **App Store distribution** certificate and an **App Store** provisioning
profile. (Ad-hoc profiles list device UDIDs and let a build be side-loaded to those devices only;
they are rejected by TestFlight and are not used here.)

Workflow `.github/workflows/ios-signing.yml` ("iOS signing (cloud)", manual) does on a GitHub macOS
runner what Keychain Access + the developer portal would do on a Mac:

1. `fastlane produce` — registers App ID `com.codyengilman.soccermaster` and the App Store Connect
   app record (idempotent).
2. `fastlane cert` — generates the private key and CSR **on the runner** and has Apple issue the
   Apple Distribution certificate.
3. `openssl` — packages key + certificate into a `.p12` protected by a random single-use password.
4. `fastlane sigh` — creates and downloads the App Store provisioning profile.
5. Unity Build Automation API — uploads `.p12` + password + `.mobileprovision` as credential set
   `SoccerMaster App Store` (optionally attaches it to the build target).

You never download, forward or type the certificate, key, profile or password; the private key
exists only on that ephemeral runner. To rotate, rerun the workflow (revoke the old certificate in
the developer portal first if Apple says the distribution-certificate limit is reached).

Secrets live on the GitHub **environment `ios-release`** (repo → Settings → Environments → New
environment → `ios-release` → Environment secrets), not at repository level: PR and CI workflows
cannot read them, and the environment's **Required reviewers** (add yourself) means every signing
or upload run waits for an explicit approval tap. All are entered in the GitHub UI from the iPhone;
none is ever committed, printed or attached:

| Secret | Where it comes from |
| --- | --- |
| `ASC_KEY_ID`, `ASC_ISSUER_ID`, `ASC_API_KEY_P8` | App Store Connect → Users and Access → Integrations → App Store Connect API → Team Keys → "+" with role **Admin** (certificates need Admin; App Manager is enough for upload only). Download the `.p8` once; paste its full text into `ASC_API_KEY_P8` |
| `UNITY_BUILD_API_KEY` | Unity Cloud → DevOps → Build Automation → Settings → API key |
| `UNITY_ORG_ID` | Unity Cloud → organization settings (the id, not the display name) |

## TestFlight upload — explicit, separate trigger

Workflow `.github/workflows/testflight.yml` ("TestFlight upload", manual) takes a finished UBA build
number and:

0. **approved-commit gate**: `approved_sha` (required, full 40-hex) must be reachable from
   `approved_ref` (default `integration/pr1-11`) — a build from an unmerged branch cannot be released;
1. fetches the build record through the UBA API and requires `buildStatus == success` **and**
   `lastBuiltRevision == approved_sha`;
2. downloads the IPA and records its SHA-256; 3. verifies bundle id, `CFBundleVersion == build
   number`, valid code signature, `get-task-allow` false, and an App Store profile (no
   `ProvisionedDevices`, not enterprise);
4. uploads with `fastlane pilot` using the App Store Connect API key and **waits for Apple
   processing** — a green run means Apple finished processing, not merely that bytes were sent;
5. writes a summary and attaches `testflight-record-<build>.json` (UBA build, commit, version,
   CFBundleVersion, Apple team, IPA SHA-256 + size, upload time, run URL; kept 400 days) — the
   release record for that build number.

Nothing is uploaded automatically after a UBA build; a person runs this once per build they want
testers to see. After it is green: App Store Connect → TestFlight → add the build to the internal
group that contains the owner's Apple ID → the TestFlight app on the iPhone shows it.

## Phone-ops checklist (once Apple enrollment is active)

1. GitHub → Settings → Environments → **New environment `ios-release`** → add yourself as Required
   reviewer → Environment secrets: `ASC_KEY_ID`, `ASC_ISSUER_ID`, `ASC_API_KEY_P8` (App Store Connect
   → Users and Access → Integrations → Team Keys, role Admin), `UNITY_BUILD_API_KEY`, `UNITY_ORG_ID`.
2. GitHub → Actions → **iOS signing (cloud)** → Run workflow with `check_only = true` → approve the
   environment prompt → the summary says whether `com.codyengilman.soccermaster` is registered to
   your team. (`false` is expected before first use; if the later create step fails with "already
   exists" the id is owned by another team and a different id must be chosen.)
3. Same workflow with `check_only = false`, `uba_buildtarget = soccermaster-ios-testflight` →
   registers the App ID + app record, issues the distribution certificate, uploads the credential
   set `SoccerMaster App Store` to UBA.
4. Unity Cloud → Build Automation → target `SoccerMaster-iOS-TestFlight` → fill the table above
   (credentials now appear in the dropdown) → **Build**. Read the build log's test section: this is
   the first licensed EditMode/PlayMode evidence.
5. Merge the reviewed native PR into `integration/pr1-11` (a release needs a commit on that branch),
   rebuild in UBA from that commit if the build was made from the PR branch.
6. GitHub → Actions → **TestFlight upload** → Run workflow: UBA build number, `approved_sha` = the
   40-char commit from the UBA build page → approve the environment prompt.
7. App Store Connect → TestFlight → add the build to the internal group → open TestFlight on the
   iPhone → install.

## Device checklist (first install on the iPhone)

* Build identity overlay (bottom-left) shows the expected `v0.1.0 (<UBA build>) · <sha7> · Unity 6000.3.24f1`.
* Routine play is visibly accelerated under the veil; a lead-in pulls the camera to the selected
  player and the picture freezes before any answer becomes tappable.
* Exactly four answer cards, all inside the safe area (no overlap with the notch / home indicator).
* A tap resolves at 1×, then the feedback panel shows Decision / Execution / Outcome and NEXT.
* Let one timer expire: the engine acts and feedback still appears (no stuck state).
* Background the app during a timer (swipe to Home), reopen: same moment, frozen, then re-armed;
  force-quit and relaunch: same match resumes (score, clock, moment count).
* Half-time and full-time screens appear; NEW MATCH starts a fresh seed.
* Report the frame feel (stutter during Resolving would indicate the frame cap `MaxFrameMs` needs tuning).

## Recovery

| Symptom | Action |
| --- | --- |
| Save rejected on launch (log `save rejected: …`) | expected after a save-format bump; the app starts a fresh match and leaves the old file in place. Delete via NEW MATCH or bump `MatchSave.Version` deliberately with a migration |
| UBA build fails in `CloudBuild.PreExport` | the manifest lacks `buildNumber`/`scmCommitId`; set `SM_BUILD_NUMBER`/`SM_GIT_SHA` env vars on the target or fix the source-control link |
| Upload workflow: "not reachable from origin/integration/pr1-11" | the UBA build was made from an unmerged branch; merge, rebuild, rerun |
| Upload workflow: "development build" / "profile lists devices" | the target uses a development or ad-hoc credential set; attach `SoccerMaster App Store` and rebuild |
| Apple: certificate limit reached | revoke the stale Apple Distribution certificate in the developer portal, rerun **iOS signing (cloud)** |
| Need to roll back a TestFlight build | TestFlight → expire the build; re-upload an older UBA build number with its own approved commit (records in the `testflight-record-*` artifacts) |

## GitHub Actions validation (`.github/workflows/unity.yml`)

Always on (no license): `project-files` (`gen_meta.py --check`, `check_project.py`), `compile-check`
(all asmdefs compiled inside `unityci/editor:ubuntu-6000.3.24f1-ios-3` against the Editor's real
assemblies), `fixtures` (web fixture regeneration + .NET parity). Licensed jobs (`tests`,
`ios-export`) run only when `UNITY_LICENSE` or `UNITY_SERIAL`/`UNITY_EMAIL`/`UNITY_PASSWORD` exist;

evidence without any license secret in GitHub.

```
python3 unity/build/gen_meta.py --check && python3 unity/build/check_project.py

```

`IosBuild.Build` (Editor/IosBuild.cs) fails with `BuildFailedException` when the required scene is
missing, the bundle id is not reverse-DNS, the version is not `major.minor.patch`, or the build
number is not a positive integer. Env: `SM_IOS_OUTPUT`, `SM_BUNDLE_ID` (default
`com.codyengilman.soccermaster`), `SM_APP_VERSION` (default `0.1.0`), `SM_BUILD_NUMBER`,
`SM_GIT_SHA`. It writes `Assets/SoccerMaster/Resources/build_info.json` (git-ignored) so the app
can display version/build/commit. Automatic signing is disabled; no team id or profile is set here.
