# SoccerMaster native (Unity 6) — side-by-side project

The web app in the repository root stays the behavioral oracle and keeps shipping through Cloudflare
Pages. This folder is the native iPhone implementation (v1.2 package, tickets N00–N08). Nothing here
replaces or alters the web build; native delivery goes Unity Build Automation → App Store Connect →
TestFlight, and every step of it runs in a cloud service (no local Mac, Xcode or Unity Editor).

```
unity/
  Assets/SoccerMaster/
    Runtime/Core/      SoccerMaster.Core   deterministic simulation port, no UnityEngine references
    Runtime/View/      SoccerMaster.View   FirstTouchController (time+input in, state out), FirstTouchRig (presentation only)
    Editor/            SoccerMaster.Editor FirstTouchSceneBuilder, IosBuild (export), CloudBuild (UBA pre-export hook)
    Scenes/FirstTouch.unity                 the one shipped scene (one root object: FirstTouchController + FirstTouchRig)
    Tests/EditMode     fixture parity + build-config tests
    Tests/PlayMode     runs the real FirstTouch scene
    Tests/Fixtures/first_touch_parity.json   GENERATED by `npm run native:fixtures` from the web code
  Packages/manifest.json                     inputsystem 1.20.0, ugui 2.0.0, test-framework 1.6.0 (Editor-bundled versions)
  ProjectSettings/                           ProjectVersion.txt 6000.3.24f1; iPhone-only, portrait, IL2CPP, ARM64
  Tools/ParityCheck/                         plain .NET harness (pre-check only, not Unity evidence)
  Tools/CompileCheck/                        license-free C# compile of every asmdef against the real Editor DLLs
  build/compile_check.sh, gen_meta.py, check_project.py, test.sh, ios.sh
```

Boundary rule (architecture/INTEGRATION.md): `FirstTouchDrill` owns state, RNG, rules and outcomes.
`FirstTouchController` only passes wall-clock time and touch input into the drill and mirrors the
drill's committed state onto the scene. `FirstTouchRig` builds camera/field/ball/players/HUD at
runtime and hands them to the controller (`Bind`). No soccer reasoning lives in a MonoBehaviour.

## First ported interaction: first-touch training

`src/training/firstTouch.ts` → `Assets/SoccerMaster/Runtime/Core/Training/FirstTouchDrill.cs`
(plus `Rng`, `Vec2D`, `JsMath`, `GestureReader`). Preserved contract: 24×18 area, receive (10,9),
server (3,9), three gates, 50 ms tick, 2.5 s real-time decision window (×1.5 accessible), 0.12×
simulated time during the window, seeded RNG, anticipatory defender, decision / execution /
outcome kept separate, timeout still commits a loose touch.

Parity is checked against fixtures the **web implementation generates**, never hand-written values:

```
npm run native:fixtures   # tools/nativeFixtures.ts → Tests/Fixtures/first_touch_parity.json
npm run native:parity     # .NET harness: replays fixture through the C# port (21,950 comparisons)
```

Tolerances: discrete state, phases, bands, gates, RNG words — exact. Kinematic doubles — 1e-9
(last-ULP differences between V8 and .NET transcendental functions).

(`gen_meta.py`; settings adapted from the 6000.3.24f1 URP template with the pipeline references
removed) because no licensed Editor has run yet. A licensed import may re-serialize them; that diff
is expected and is what the `tests` job in `unity.yml` reports, it must not add or remove assets.

Local Linux box: Unity 6000.3.24f1 Editor + iOS module installed and runnable (`Unity -version`
OK, activation file generated) but every project operation exits 198
`No valid Unity Editor license found`. Personal licenses cannot be activated from the command line,
so licensed validation happens in Unity Build Automation (below) or GitHub Actions once a
`UNITY_LICENSE` secret exists.

## Signing — App Store distribution, prepared entirely in the cloud

TestFlight requires an **App Store distribution** certificate and an **App Store** provisioning
profile. (Ad-hoc profiles list device UDIDs and let a build be side-loaded to those devices only;
they are rejected by TestFlight and are not used here.)

Workflow `.github/workflows/ios-signing.yml` ("iOS signing (cloud)", manual) does on a GitHub macOS
runner what Keychain Access + the developer portal would do on a Mac:

1. `fastlane produce` — registers App ID `com.codyengilman.soccermaster` and the App Store Connect
   app record (idempotent).
2. `fastlane cert` — generates the private key and CSR **on the runner** and has Apple issue the
   Apple Distribution certificate.
3. `openssl` — packages key + certificate into a `.p12` protected by a random single-use password.
4. `fastlane sigh` — creates and downloads the App Store provisioning profile.
5. Unity Build Automation API — uploads `.p12` + password + `.mobileprovision` as credential set
   `SoccerMaster App Store` (optionally attaches it to the build target).

You never download, forward or type the certificate, key, profile or password; the private key
exists only on that ephemeral runner. To rotate, rerun the workflow (revoke the old certificate in
the developer portal first if Apple says the distribution-certificate limit is reached).

Secrets (GitHub → repo → Settings → Secrets and variables → Actions). All are entered in the
GitHub UI from the iPhone; none is ever committed, printed or attached:

| Secret | Where it comes from |
| --- | --- |
| `ASC_KEY_ID`, `ASC_ISSUER_ID`, `ASC_API_KEY_P8` | App Store Connect → Users and Access → Integrations → App Store Connect API → Team Keys → "+" with role **Admin** (certificates need Admin; App Manager is enough for upload only). Download the `.p8` once; paste its full text into `ASC_API_KEY_P8` |
| `UNITY_BUILD_API_KEY` | Unity Cloud → DevOps → Build Automation → Settings → API key |
| `UNITY_ORG_ID` | Unity Cloud → organization settings (the id, not the display name) |

## TestFlight upload — explicit, separate trigger

Workflow `.github/workflows/testflight.yml` ("TestFlight upload", manual) takes a finished UBA build
number and:

1. fetches the build record through the UBA API and requires `buildStatus == success` (and the
   expected commit, if you pass one);
2. downloads the IPA; 3. verifies bundle id, `CFBundleVersion == build number`, valid code signature,
   `get-task-allow` false, and an App Store profile (no `ProvisionedDevices`, not enterprise);
4. uploads with `fastlane pilot` using the App Store Connect API key and **waits for Apple
   processing** — a green run means Apple finished processing, not merely that bytes were sent;
5. writes a summary (build, commit, version, team).

Nothing is uploaded automatically after a UBA build; a person runs this once per build they want
testers to see. After it is green: App Store Connect → TestFlight → add the build to the internal
group that contains the owner's Apple ID → the TestFlight app on the iPhone shows it.

## Order of operations from the iPhone (once Apple enrollment is active)

1. App Store Connect → create the API key (Admin) → add the three `ASC_*` secrets on GitHub.
2. Unity Cloud → Build Automation → Settings → copy API key → add `UNITY_BUILD_API_KEY`, `UNITY_ORG_ID`.
3. GitHub → Actions → **iOS signing (cloud)** → Run workflow (`uba_buildtarget = ios-testflight`).
4. Unity Cloud → the iOS target → fill the table above (credentials now appear in the dropdown) → Build.
5. GitHub → Actions → **TestFlight upload** → Run workflow with that UBA build number.
6. App Store Connect → TestFlight → add build to the internal group → open TestFlight on the iPhone.

## GitHub Actions validation (`.github/workflows/unity.yml`)

Always on (no license): `project-files` (`gen_meta.py --check`, `check_project.py`), `compile-check`
(all asmdefs compiled inside `unityci/editor:ubuntu-6000.3.24f1-ios-3` against the Editor's real
assemblies), `fixtures` (web fixture regeneration + .NET parity). Licensed jobs (`tests`,
`ios-export`) run only when `UNITY_LICENSE` or `UNITY_SERIAL`/`UNITY_EMAIL`/`UNITY_PASSWORD` exist;
they are skipped, never faked. UBA's own EditMode/PlayMode switch is the cloud path to the same
evidence without any license secret in GitHub.

## Repeatable entry points

```
UNITY_EDITOR_DIR=/path/to/6000.3.24f1/Editor unity/build/compile_check.sh   # no license needed
python3 unity/build/gen_meta.py --check && python3 unity/build/check_project.py
UNITY_EDITOR=/path/to/Unity unity/build/test.sh all        # EditMode + PlayMode, XML in build/logs
UNITY_EDITOR=/path/to/Unity SM_BUILD_NUMBER=42 unity/build/ios.sh
```

`IosBuild.Build` (Editor/IosBuild.cs) fails with `BuildFailedException` when the required scene is
missing, the bundle id is not reverse-DNS, the version is not `major.minor.patch`, or the build
number is not a positive integer. Env: `SM_IOS_OUTPUT`, `SM_BUNDLE_ID` (default
`com.codyengilman.soccermaster`), `SM_APP_VERSION` (default `0.1.0`), `SM_BUILD_NUMBER`,
`SM_GIT_SHA`. It writes `Assets/SoccerMaster/Resources/build_info.json` (git-ignored) so the app
can display version/build/commit. Automatic signing is disabled; no team id or profile is set here.
